# The table write contract is shown read-only in three places, and supplemental SQL is one task-level download

`dbx-prototype` expresses DDL as five switches on wizard step 4 (primary key, indexes, defaults, foreign keys, comments). ADR-0011 makes DDL a read-only rendering of the table write contract (表写入契约), and #45 lists "DDL as the presentation of the table write contract" as a floor the prototype port may not give up. ADR-0011 also left open when supplemental SQL (补建 SQL) is generated and where the DBA receives it. Decided in [#51](https://github.com/liumingjian/dbx/issues/51).

## The switches are cut

None of the five switches has a v1 capability behind it. The source primary key is always built (#23); only promoting a unique-index candidate on a table without one is a per-table choice, and the operator may decline it. Defaults follow ADR-0011's whitelist. Indexes, foreign keys, and comments go to supplemental SQL. The whole 建表选项 (DDL options) block is cut, not disabled: a disabled switch tells the DBA the platform could do this. Its place holds one read-only line: the target table carries columns, types, `NOT NULL`, primary key, and identity; indexes, foreign keys, comments, and the rest go to supplemental SQL. 建表选项 is retired as a term. DDL stays read-only. X2Doris-style full-text editing stays rejected for ADR-0011's reason: DBX cannot prove edited SQL.

## Where the contract rendering appears

1. **Wizard stage 4, per-table drawer**: the complete read-only DDL, as ADR-0020 already places it, plus a 补建 SQL tab previewing that table's supplemental SQL before execution.
2. **Wizard stage 5, execution confirmation**: counts only, each one opening the affected tables' drawers: tables with a primary key, tables without one, columns whose `NOT NULL` was relaxed, and objects deferred to supplemental SQL. Hundreds of full DDL texts are not reviewable on one page.
3. **Task detail, 运行快照 (run snapshot) tab**: each table's DDL as frozen for that run. A rerun regenerates the contract, so the DDL a run actually executed is only in its own snapshot.

## Structural proof

Structural proof (结构证明) is a per-table gate, shown on the table migration unit and nowhere else. When it passes, the unit's timeline step under 创建目标表中 reads 结构证明通过. When it fails, the unit ends 迁移失败 with a reason code naming the target-creation stage. The table evidence drawer shows the structured difference (coordinate, expected, actual, violated invariant), translated through the error translation layer (ADR-0005), with the raw difference collapsed. There is no task-level proof summary: a failed unit is already red in 运行监控.

Structural proof is never a preflight finding (预检发现): it runs after baseline and DDL, after approval ([#86](https://github.com/liumingjian/dbx/issues/86)). After recording the difference as evidence, the failed unit drops the table it just created, under the advisory lock and only while introspection shows the generation is still this run's, the table has zero rows, and no Sink was created. If any check fails, the table stays, and a rerun meets it as the blocking finding "an existing target table differs from the contract" (ADR-0029). Otherwise a rerun of the table follows the ordinary creation path.

## Supplemental SQL

- **Content.** Unique constraints, ordinary indexes, foreign keys, and table and column comments are executable statements. A B-tier default that translates to `ALTER COLUMN … SET DEFAULT` is executable too. `ON UPDATE CURRENT_TIMESTAMP` and collation appear only as SQL comments giving the source definition and "requires manual handling": #23 forbids generated triggers, and collation has no reliable PostgreSQL equivalent. Foreign keys come last.
- **Follows mapping rules.** Every table and column name is the approved target name. A statement touching a pruned column, or a foreign key referencing a table outside the migration scope, is emitted commented out with the reason. Nothing is silently dropped; the script exists so that no source structure is lost.
- **Timing.** It is generated by the same pure function, from the same metadata snapshot, as the contract. It exists from wizard stage 4 onward and is frozen per run.
- **Task-level, not run-level.** Under ADR-0024 a task can finish across several runs, and foreign keys cross those batches. The downloadable script is assembled per task from each table's latest successful run. Its header lists the tables not yet 迁移完成 and warns that running it before the 整库结论 (whole-database conclusion) is green may fail on those tables.
- **Delivery.** A 下载补建 SQL (download supplemental SQL) button in the task detail header produces one `.sql` file. It is not written to the server's disk, which the DBA may not be able to reach. It is not embedded in the validation report, a change-review artefact that states only the number of deferred objects and points at the script. DBX never executes it.

## Considered options

- **Keep the switches disabled** was rejected: it advertises configurability that v1 does not have.
- **Editable DDL** (X2Doris) was rejected again, for ADR-0011's reason.
- **Supplemental SQL per run** was rejected: cross-batch foreign keys would be split across files the DBA must stitch together.
- **Generating supplemental SQL only after migration** was rejected: the DBA should see what will not be built before approving execution.
- **A task-level structural proof view** was rejected: it repeats per-unit state already visible in run monitoring.
