# Platform-owned DDL and table write contract

DBX v1 creates and proves every target table before Kafka Connect Sink may write to it. The immutable table write contract is the single source of truth for DDL rendering, target structural proof, routing, Connect schema and JDBC binding compatibility, and Sink configuration. DDL is a complete read-only rendering of that contract, never a second editable configuration.

## Contract assembly and approval

The migration core assembles one contract per table migration unit from normalized MySQL metadata, the directed database pair's mapping decisions, structured mapping rules, exact preflight findings, identifier and routing decisions, connector policy, and approved target coordinates. It records ordered selected columns, exact source-output and target names, Connect/Avro types, JDBC binder families, PostgreSQL types and parameters, nullability, supported defaults, primary-key order, identity or sequence intent, routing, notices, version identities, approval revision, and a deterministic fingerprint.

A mapping change creates a new draft and reruns every affected preflight. Only a `SUPPORTED` preflight conclusion may be approved. The contract belongs to the table, not its box. A rerun reads fresh metadata and facts and creates a new run-local contract snapshot; even a zero-difference contract requires confirmation under ADR-0006.

Schema, table, and column identifiers are preserved character-for-character and always quoted. A first run encountering an existing target table fails review rather than reusing, truncating, or replacing it. One source MySQL database maps to one target PostgreSQL schema. Column pruning or renaming uses a single-table Source query so the resulting Connect field name already equals the approved target name; changing only the DDL would violate the Sink contract. Collision, length, or Kafka-name exceptions use the recorded safe routing path and an isolated box.

## DDL and structural proof

After the source write freeze and exact baseline are fixed, DBX executes target DDL derived solely from the approved contract. The v1 writable-table boundary contains columns and exact types, `NOT NULL` except the approved per-column zero-date relaxation, a primary key when supported or unambiguously promoted, and `GENERATED BY DEFAULT AS IDENTITY` or an owned explicit sequence for `numeric(20,0)` auto-increment columns. PostgreSQL B-tree width and source auto-increment bounds are preflight obligations.

Literal defaults and `CURRENT_TIMESTAMP(n)` translated to `LOCALTIMESTAMP(n)` form the supported default whitelist. `ON UPDATE CURRENT_TIMESTAMP`, unknown or generated default expressions, zero-date defaults, triggers, unique constraints other than the primary key, ordinary indexes, foreign keys, comments, and collation are outside the live v1 contract. DBX preserves their source metadata in supplemental SQL but does not execute that script during migration. The exact generation time and delivery surface of supplemental SQL remain a product-shell decision, not permission to add those structures to the migration path.

Immediately after DDL, DBX reads PostgreSQL system catalogs and compares the actual base table with the contract. Proof requires character-exact coordinates, no missing or extra columns, normalized exact types and parameters, nullability and supported defaults, primary-key order, identity or sequence default and ownership, mechanically evaluated routing, and compatibility between every Connect type, JDBC binder, and target type. Column order is recorded and generated deterministically but is not independently a Sink compatibility failure. Any difference is structured blocking evidence and prevents Sink provisioning.

DBX never proves a production target by inserting and deleting a fabricated row. Such a row cannot cover real value domains and can advance sequences, trigger audit behavior, or duplicate mapping logic. Source value risks belong to exact preflight and real end-to-end certification; structural risks belong to deterministic catalog proof.

## Sink contract

Every v1 JDBC Sink fixes at least:

- `auto.create=false`
- `auto.evolve=false`
- `insert.mode=insert`
- `pk.mode=none`
- `delete.enabled=false`
- `quote.sql.identifiers=always`

The normalized configuration and routing are derived from the same frozen contract and enter the execution fingerprint. Sink starts only after structural proof and its required object privileges are proven. It does not own target DDL, infer a schema, widen a column, create a missing field, or repair drift.

The target account model, isolated capability probe, exact object grants, target leases, generations, and rerun truncation are governed by ADR-0006. An existing target is acceptable only in the explicit rerun path after zero-difference proof, lease acquisition, destructive-scope confirmation, advisory locking, and fact re-read.

## Consequences

Errors that Connect would otherwise reveal on the first real batch become deterministic approval or target-preparation failures. Users review a complete DDL rendering while changing only bounded mapping rules, so the common path stays automatic without permitting SQL that DBX cannot prove.

The contract model requires exact type mapping, metadata normalization, PostgreSQL introspection, binder compatibility tests, and versioned snapshots. V1 intentionally creates a minimal writable table rather than claiming full structural migration; supplemental SQL makes omitted source structures visible and recoverable without burdening transfer correctness.

## Rejected alternatives

- **Sink `auto.create` or `auto.evolve`** was rejected because successful insertion would not prove type fidelity, identifier equality, target constraints, or approved intent.
- **Editable DDL** was rejected because arbitrary SQL can diverge from Source output and bypass structured preflight and mapping rules.
- **A production probe insert** was rejected because one fabricated value cannot prove the real domain and may cause irreversible side effects.
- **Reusing an existing table on the first run** was rejected because ownership and structural history are unproven.
- **Creating all source indexes, foreign keys, defaults, comments, and collation before transfer** was rejected because v1 optimizes a correct writable migration path, not complete structure conversion.
