# Preflight-gated large-record envelope

DBX v1 supports a source row only when every individual value and the row's total pre-serialization payload are each at most 20 MiB (20,971,520 bytes). Length means bytes in the source representation, not characters and not the compressed or Avro-encoded Kafka record. A table becomes a large record table when either boundary exceeds 1 MiB; it receives an isolated box even if it remains within the supported envelope. This preserves the distinction between a business support limit and Kafka's transport limit.

Preflight is exact and mandatory before DDL approval. For every approved Source extraction expression `E`, including an aliased expression used by query mode, DBX defines its source-byte length as `COALESCE(OCTET_LENGTH(CAST(E AS BINARY)), 0)`; `NULL` therefore contributes zero bytes. The per-value check is the maximum of that expression for each selected column, and the row check is the maximum of their sum. This is an intentionally stable source-side metric, not an estimate of JDBC objects or Avro output; the separate 5 MiB transport allowance absorbs representation and protocol overhead. DBX evaluates all per-value maxima and the row maximum in one aggregate query per table, never one scan per column. The scan runs before the source baseline is captured and may execute while writes continue, because it is a capability check rather than a count or content baseline. DBX does not sample or infer a pass from `information_schema`: either the exact scan succeeds or the table remains blocked. Query timeout is configurable as an advanced deployment setting; timeout, cancellation, permission failure, or any other inability to prove the envelope is an `INCONCLUSIVE` preflight and cannot be overridden into a runnable table.

A value or row above 20 MiB is an unsupported-table result, not a migration failure. The DDL review uses this exact red warning: **“无法迁移：表 `<table>` 的 `<column or row>` 最大为 `<observed bytes>` 字节，超过 DBX v1 的 20 MiB（20,971,520 字节）上限。请选择排除此表、裁剪超限字段后重新预检，或中止并在源端缩减数据；不能忽略此限制继续迁移。”** An inconclusive scan substitutes **“无法确认是否可迁移：DBX 未能完成 20 MiB 精确预检（`<reason>`）。修复权限、超时或连接问题后重试；不能忽略此检查继续迁移。”** The available exits are to exclude the table, exclude an offending selected column through the column-pruning/query-mode behavior already fixed by the map, or cancel review and change the source outside DBX. Excluding one field does not waive the row check: DBX reruns preflight against the approved selected columns. DBX never silently truncates, samples, or routes an over-limit table outside Kafka.

Kafka uses 25 MiB (26,214,400 bytes) as a separate transport envelope. For DBX-managed infrastructure, deployment configures broker `message.max.bytes` and `replica.fetch.max.bytes`; the Connect worker has a 4 GiB heap, runs on a deployment with at least 8 GiB memory (16 GiB and four CPU cores recommended), allows connector client overrides, and uses a 128 MiB producer buffer. DBX disables Connect topic auto-creation and explicitly creates every data and dead-letter topic with `max.message.bytes=26214400`. Source connectors set `producer.override.max.request.size=26214400`, `producer.override.buffer.memory=134217728`, compression to `zstd`, and `producer.override.max.in.flight.requests.per.connection=1`. Sink connectors set `consumer.override.max.partition.fetch.bytes=26214400`, `consumer.override.fetch.max.bytes=52428800`, `consumer.override.max.poll.records=1`, and `consumer.override.max.poll.interval.ms=900000`. Producer `batch.size` remains 16 KiB so a large record forms its own batch. These large-record settings are part of the execution signature; ordinary tables do not inherit the single-record poll limit.

External Kafka and Connect are admitted through an active capability check before DDL approval. DBX must be able to create a disposable topic with `max.message.bytes=26214400`, read that effective config back, and round-trip an incompressible probe whose serialized Kafka record batch is between 26,214,000 and 26,214,400 bytes; this proves the usable boundary rather than merely proving that 20 MiB fits. It must also validate the exact connector-level overrides and delete the probe topic. The source probe contains generated non-sensitive bytes and uses the same serializer and producer configuration as a migration; the consume leg uses the same consumer limits as Sink. Failure blocks the run with an administrator checklist; DBX does not lower the declared support boundary or proceed on an unverified cluster. Topic deletion may complete asynchronously and is reported separately from probe success.

Runtime oversize remains possible if source data changes after preflight and before the externally enforced write freeze, or if encoded overhead exceeds the 5 MiB transport allowance. A producer-side `RecordTooLargeException`, broker `MESSAGE_TOO_LARGE`, large-message buffer allocation timeout, or equivalent sink/DLQ size failure stops the affected box, preserves topics and target data, and marks its table migration units failed. The translated error says which transport boundary rejected the record, reports the serialized size when available, and instructs the operator to keep the write freeze, inspect source byte lengths, then create a new migration run after excluding or reducing the data. DBX never retries an oversize record automatically and never logs record values; raw stack traces remain available without `errors.log.include.messages`.

Kafka retention is not a safety valve for this envelope. Topics and records remain available until the lifecycle decision permits explicit deletion after validation or discard. Size- or time-based retention must not delete unvalidated data, because that would convert capacity pressure into silent target data loss.

## Considered options

- Defining 20 MiB only per field was rejected because two individually valid fields can form an untransportable row.
- Defining the limit on Avro-serialized or compressed bytes was rejected because it makes support depend on schema details and compression ratio, cannot be proven cheaply in source SQL, and produces unstable user-facing behavior.
- Sampling large tables or trusting `information_schema` estimates was rejected because a single missed row fails a whole box at runtime; a slower exact scan is preferable in an offline migration product that prioritizes correctness.
- Allowing users to acknowledge and continue after an inconclusive or over-limit preflight was rejected because Kafka is the only v1 data path and there is no truthful degraded mode.
- Treating short Kafka retention as bounded-storage backpressure was rejected because retention can delete records before Sink consumption or validation.

## Consequences

Preflight may require a full source-table scan and can delay review, but it scans candidate columns together and never consumes the write-freeze window. External-cluster installations require create, describe, produce, consume, delete, and Connect validation privileges before DBX can promise the same 20 MiB support as its managed deployment. Large-record tables trade throughput for a bounded Connect heap footprint through isolation and single-record polling. The 25 MiB transport allowance is a versioned compatibility constant: connector, serializer, or Kafka upgrades must rerun boundary tests at exactly 20 MiB payload and just above the business limit before release.
