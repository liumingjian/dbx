# Slices are tracer-bullet vertical slices, and an ADR is revised by the work that tests it

`docs/spec/README.md` §How to use it made the slice unit a group of obligations inside one module, and ADR-0018 §Session rule made one session change one module. Neither recorded the alternative it was choosing against. `mattpocock-skills:to-tickets`, the skill that drafts every implementation ticket, states the opposite in its `<vertical-slice-rules>`: "Each slice cuts a narrow but COMPLETE path through every layer (schema, API, UI, tests): vertical, NOT a horizontal slice of one layer." The conflict was never adjudicated — it was resolved silently, in favour of the ADR, nine specs in a row. Resolved in [#154](https://github.com/liumingjian/dbx/issues/154).

- **A slice is a tracer-bullet vertical slice, and that design rule has first priority.** It is a general design convention, not a DBX preference, so it outranks any DBX convention that merely happens to be convenient for scheduling. A slice cuts a narrow but complete path through every layer it needs — schema, module `api`, implementation, adapter, UI, tests — and is demoable on its own. Where a DBX rule and this rule disagree, this rule wins and the DBX rule is amended, not the other way round.
- **An ADR is revised by the work that tests it.** An ADR records the best ruling available when it was written; implementation is what discovers whether it was right. A rule whose stated premise has expired is not thereby binding, and "an ADR says so" is not an argument for keeping it. This is already how this corpus behaves — ADR-0018's own module table and pure-core list are marked superseded by ADR-0036, ADR-0003's large-record consequence was amended by ADR-0040 — and it is now stated rather than inferred from the pattern.
- **ADR-0018 §Session rule is amended: one session changes one slice, which may span modules.** Its replacement text is "One session implements one slice. A slice may touch several modules; it sees each one only through its `api`." The rule it replaces required a cross-module change to be split into an interface-first session followed by one session per consumer, which is the interface-first horizontal pattern this ADR rejects.
- **The session rule's premise had expired, which is the narrower reason it falls.** ADR-0018 opens "DBX is built entirely by agents working in 100K-token sessions", and every consequence of the session rule was derived from that figure. `connection` was implemented in a 1M-token session. The rule is not being overturned because a skill outranks it; it is being overturned because the number it rested on is no longer true, and the first bullet then decides what replaces it.
- **No ArchUnit rule changes, and no module boundary moves.** ADR-0018 §Enforcement's four rules constrain dependency direction and `api`-only access — a reference into another module's non-`api` package, a dependency cycle, a pure module depending on `JdbcTemplate`/an HTTP client/a clock, and a caller other than `orchestration` referencing `workflow.api.command`. None of them constrains how many modules one session touches, so a vertical slice crossing four modules breaks none of them. The session rule was prose enforced by nothing, which is why this amendment costs no test. ADR-0036's module table, ownership and one-way dependencies are untouched.
- **A leaf module cannot be sliced vertically on its own, and that is an argument about ticket scope, not an exemption.** `connection`'s only side effect is reading one file: it has no schema, no UI and no HTTP, so "every layer" inside it is `api` plus implementation plus tests. A tracer bullet through credential crypto necessarily also touches `orchestration` and `web`. Such a module therefore gets no slices of its own; its capabilities are carried by the slices of the vertical paths that need them.
- **The ruling applies to slicing not yet done, because slicing already built cannot be recut.** `dialect`'s five specs and `connection`'s four are merged; their code exists and re-slicing them would change nothing. Each remaining sub-spec's §Slices section is recut as vertical tracer bullets when that module's work is next planned, not in one sweep — consistent with the map's standing guardrail that tickets are generated one at a time because the map is an index, not a warehouse.
- **The ticket-drafting gate must read this ruling, or it will keep confirming the deviation.** #154 established that the audit which approved `connection`'s four tickets measured them against `docs/spec/connection.md` §Slices and found them faithful, which they were. A rubric of fidelity to a slice table cannot detect that the slice table is horizontal. `docs/spec/README.md` §How to use it therefore states the vertical-slice rule directly, so a session drafting tickets meets it without having to reach an ADR.

## Considered options

- **Keep module-horizontal slicing and record it as the ruling.** Rejected: it preserves the concrete damage #154 documented — an interface frozen and ArchUnit-guarded before any consumer could contradict it — and it keeps a rule whose 100K-token premise has expired.
- **Keep it, and add a consumer-first obligation** requiring a module's last slice to land one real consumer call site, or deferring the interface freeze until the first consumer compiles. Rejected as the ruling, though it is the right migration aid: it treats the symptom of interface-first slicing while leaving interface-first slicing in place. Its effect follows anyway from the first bullet, because a vertical slice contains its own consumer.
- **A hybrid**: module slices for pure and leaf modules, vertical slices where there is a user-observable outcome. Rejected: it reproduces the ambiguity this ADR exists to remove, and the leaf-module bullet above already says what happens to a module that cannot be sliced alone.
- **Changing the skill instead, to match the ADR.** Rejected: the skill states a general design convention, and a project convention that contradicts one should lose or say why. This ADR is the "say why" and it concluded the project convention was wrong.
- **Recutting all fourteen remaining sub-specs' §Slices in one pass.** Rejected: fourteen 15,000-character documents rewritten against a slice graph nobody has yet planned would be speculation, and it would invalidate the computable frontier for work that is months away.

## Consequences

ADR-0018 §Session rule is replaced and its 100K-token premise is marked expired. `docs/spec/README.md` §How to use it states the vertical-slice rule and stops making the sub-spec §Slices section the unit of a session. No ArchUnit rule, module boundary or ownership row changes, and nothing already merged is reopened.

The cross-module slice graph in §Where to start no longer follows from a module build order, because a vertical slice starts at the UI and reaches down. That graph is recut per initiative as work is planned, and `docs/spec/`'s sub-specs become what they always were in fact — the per-module obligation and ownership reference a slice consults — rather than the thing that defines a session's scope.

Modules with no user-observable surface of their own, `connection` first among them, stop having independent slices: their capabilities arrive as part of the vertical paths that consume them. The practical cost is that a leaf module's `api` is no longer frozen in advance of its consumers, which is the outcome #154 asked for.
