# Environment check detects and explains; DBX holds no host control

> Amended by [ADR-0031](0031-platform-memory-budget-admission-and-bounded-in-flight-records.md). E5 becomes a memory-tier check: host memory against the tier, and the effective Connect and Kafka heaps, read over JMX on the Compose network only. JVM heap is therefore no longer unobservable. Container memory limits still are.

V1 ships a platform-owned single-node Kafka, Connect, and Schema Registry beside DBX in Docker Compose, so it is tempting to let DBX repair its own runtime: restart sibling containers, rewrite drifted Compose parameters, restore memory limits. We decided DBX does not do that. The **environment check** (环境自检) detects and explains; it does not remediate. DBX never mounts `docker.sock` or runs a host agent, and ADR-0005's rule that DBX never changes configuration automatically stays whole. The only self-healing is Docker's own: `restart: unless-stopped` and healthchecks declared in the shipped Compose file.

Why: host control through `docker.sock` is equivalent to root on the customer's host, and the target customers (state-owned, finance, government, all air-gapped) will likely reject it in security review, taking the distribution shape with it. Parameters that drift at the worker, JVM, or container-limit level are usually an operator's deliberate response to a crowded host; silently reverting them fights the customer's operations team. And the objects DBX does create — connectors and topics — are already run-scoped and immutable (ADR-0001, ADR-0006): when one drifts or disappears the run fails rather than being rebuilt, so nothing is left for automatic repair.

## Shape

- **When.** A full check at platform startup, and a run-scoped check before a migration run is admitted. Continuous in-run observation belongs to the runtime observation surface (#55), reusing ADR-0002's disk thresholds; there is no install-time-only check.
- **Catalog.** E0 diagnosis catalog integrity (ADR-0005's startup validation, folded in); E1 customer-supplied MySQL Connector/J present with a release-allowlisted checksum; E2 Kafka / Connect / Schema Registry ready within a bounded readiness budget; E3 Connect plugin inventory matches the release; E4 drift of the #6-critical parameters observable through Kafka AdminClient and service APIs, compared with the release's expected-configuration snapshot; E5 host memory at least 8 GB; E6 Kafka log-dir free space (via `describeLogDirs`) at least 50 GB at startup and at least twice the run's largest table before admission; E7 H2 metadata directory writable with headroom. Source/target reachability and privileges are not a separate item: the per-run capability check of ADR-0006 is reused and reported in the same list. Deliberately not checked: worker/JVM settings and container memory limits (not observable through the APIs DBX has) and clock/timezone (covered by ADR-0006's instance facts).
- **Conclusions.** Each item concludes satisfied (满足), unsatisfied (不满足), or inconclusive (无法判定). Inconclusive blocks exactly like unsatisfied and cannot be acknowledged away, for the reason ADR-0003 gives for `INCONCLUSIVE` preflight.
- **Consequence of failure.** At startup DBX still starts, serves the UI, and can export a diagnostic package; it refuses only to start migrations until a re-check passes. Before admission, the run enters the existing **attention required** (需要人工处理) status; no new status is introduced. Guidance names the item, observed versus expected value, the exact action, and who acts — the DBA or the server administrator, since freeing disk, placing the JAR, and restoring Compose need host access.
- **Diagnoses.** Failures are ordinary error occurrences with structured diagnoses in the one ADR-0005 catalog, under a new classification phase `ENVIRONMENT_CHECK`, with stable non-reused codes; they do not count toward the 20 external-translation rule families.
- **Evidence.** The pre-admission conclusions (per item: conclusion, observed and expected value, expected-snapshot version, catalog version) freeze into the run snapshot with ADR-0006's other run-version facts. Startup conclusions keep only the latest. The diagnostic package (#56) must carry both the run's frozen conclusions and a fresh check taken at export, side by side.

## Considered options

- **Mount `docker.sock`; DBX fully self-heals.** Rejected for the security-review and operator-conflict reasons above.
- **Carve an ADR-0005 exception letting DBX restore configuration it created.** Rejected: run immutability already turns such drift into a run failure, so the exception would buy nothing.
- **Host-side supervisor daemon.** Rejected: a second installable with host privileges, the same review problem in another form.
