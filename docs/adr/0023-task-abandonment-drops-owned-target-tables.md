# Abandoning a migration task drops the target tables DBX still owns

A DBA taking a production cutover to a change board is first asked for the rollback plan: if the migration fails or the business switches back to MySQL, what happens to the target? ADR-0006 left the target in place — cancellation (取消) keeps everything, and discard (丢弃) only truncates and "does not drop the table or schema by default". Because DBX owns target DDL (ADR-0011) and v1 never writes into a pre-existing table ([#46](https://github.com/liumingjian/dbx/issues/46): a same-name table is a blocking preflight finding), every target table was created by DBX. Owning creation without owning removal would keep only half of "DBX owns DDL". DBX v1 therefore adds **abandonment** (废弃): a task-level, separately confirmed action that removes what the task created ([#61](https://github.com/liumingjian/dbx/issues/61)).

- **Scope is the migration task, not a run.** Rolling back means giving up the migration, not one attempt: after run 1 and a partial re-migration, the DBA wants all tables gone without reasoning about target generations. Abandonment drops every target table whose current target generation belongs to any run of the task. It requires that no run of the task is nonterminal (a running run is first cancelled and must converge). An abandoned task is closed permanently: no re-migration, no new run. Copy as migration draft (复制为迁移草稿) stays available and starts a new task from scratch. Discard keeps its run-level meaning unchanged.
- **What is removed.** First, discard's existing cleanup of run-local resources for every run of the task (connectors, topics, subjects, secret projections, in ADR-0006 order). Then each owned table with `DROP TABLE` and never `CASCADE`; its IDENTITY or `OWNED BY` sequence goes with it. The schema is dropped only when DBX recorded that it created the schema, and only if the schema is empty afterwards. A schema that existed before the task is never touched. Foreign keys are never removed automatically. A table that a customer object depends on, such as a foreign key added after cutover, is refused and named, not forced.
- **Identity, not name.** When DBX creates a table, the target generation records the table's PostgreSQL object identity (`pg_class` OID). A table whose OID no longer matches has been replaced by someone else and is refused. A table whose row count differs from what its generation wrote holds data written after the migration, typically post-cutover business writes. It is marked red and needs its own explicit acknowledgement, but it does not block, because a post-cutover rollback is the case a rollback plan exists for. Syncing that data back to MySQL is CDC and stays out of scope.
- **Confirmation renders the destruction first.** Under the target lease, DBX produces the **abandonment list** (废弃清单): every object to be dropped with OID, current and migrated row counts, and differences; every refused object with its reason; whether the schema goes; and the run-local resources. The list is exportable. The operator ticks that they have read it, ticks separately for any red row difference, and types the target schema name. DBX takes an H2 backup, then before each table takes the advisory lock and rereads OID, generation, and row count. Any drift from the confirmed list skips that table and needs a fresh confirmation.
- **Before any run exists**, an approved migration draft can export a **projected abandonment list** (预估废弃清单), rendered from the table write contracts: which tables would be created, whether DBX would create the schema, and that abandonment never cascades. It is labelled projected and is never a confirmation. It is the attachment that answers the change board's rollback question.
- **Failure is resumable per table.** Each drop follows ADR-0004's external-mutation pattern: persist the intent, `DROP`, reread the catalog, commit the evidence. An already-absent table counts as success. The task is **abandoning** (废弃中) and keeps holding the target lease until every table is resolved. Retrying continues with the remaining tables without reconfirmation, unless the set changed. Refused tables leave the task **partially abandoned** (部分废弃), which can be retried after the DBA removes the blocker; the refused tables go through a fresh list and confirmation.
- **Records stay.** Abandonment deletes target data and run-local resources, never H2 evidence: the timeline, validation reports, error occurrences, and report export remain readable. Every run keeps its original run status and technical outcomes. v1 has no task deletion; abandonment is the only way to close a task.

## Task lifecycle

ADR-0004 gave the migration task no state of its own beyond the projection of its latest run. Abandonment is the first fact that belongs to the task rather than to an execution attempt, so the task gains a small lifecycle above that projection: **active** (进行中, showing the latest run's projection as before) → **abandoning** (废弃中) → **abandoned** (已废弃) or **partially abandoned** (部分废弃). This is distinct from `FAILED` and `CANCELLED`, which describe what an execution attempt did. Abandonment describes a decision about the migration as a whole, and it never rewrites run facts.

## Considered options

- **Extending run-level discard to drop tables** was rejected: the operator would have to discard runs one by one in generation order to roll back once.
- **Truncating instead of dropping** was rejected: empty DBX-created tables left in a customer schema are debris that the DBA cannot attribute, and ownership of the DDL implies ownership of removal.
- **`CASCADE`, or automatically removing dependent foreign keys**, was rejected for the same reason as in ADR-0006: it reaches customer objects outside the confirmed scope.
- **Blocking on a row-count difference** was rejected: it would make the post-cutover rollback, the main reason the feature exists, impossible.
- **A checkbox-only confirmation** was rejected: this is the only product action that deletes user data, and typing the schema name is deliberate friction.

## Consequences

The target-creation path must record two new facts: the table's OID in its target generation, and whether DBX created the schema. The management account already owns every DBX-created table (ADR-0006), so `DROP` needs no new privilege.
