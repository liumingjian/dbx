# External completion detection and run-isolated connector lifecycle

Kafka Connect connectors do not complete an offline migration: they remain `RUNNING`, bulk sources repeat the full query, source offsets are delayed or absent, and connector names retain internal offsets. DBX therefore owns the lifecycle outside Connect. Every migration run receives an immutable run ID, every box receives a box ID, and connector and topic names include both IDs so retries never inherit prior offsets.

DBX distinguishes three boundaries. A box is **read complete** when every fresh topic's end offset equals its table's exact frozen-source row count, all Source tasks are healthy, and production is stable for two 10-second polls; DBX then deletes the Source connector. It is **write complete** only after the Source is gone, every Sink lag is zero, every target row count equals the source baseline, and those signals remain stable for two polls; DBX then deletes the Sink and starts per-table validation. A table is **migration complete** only after its enabled validations pass. Source-offset REST data and connector `RUNNING` status are diagnostic signals, never completion gates. Source writes remain externally frozen until every table reaches a validation terminal state.

Connectors start Sink-first and stop Source-first. Every REST mutation is idempotently reconciled by reading current state: an existing connector is accepted only when its normalized configuration fingerprint matches; timeouts and `409` responses trigger fact re-reads and bounded retry, never blind recreation. On platform restart, the metadata database is authoritative for which nonterminal runs to reconcile, while Kafka, Connect, and PostgreSQL provide current observed state. Missing connectors before their recorded boundary fail the box rather than being recreated; unknown `dbx-` connectors are reported as orphans and never deleted automatically.

A healthy box with no observable progress for two minutes is warned; after ten minutes it is `STUCK`. DBX deletes its connectors but preserves topics and target data. Failure and cancellation likewise stop execution while preserving evidence. A separately confirmed **discard** operation removes target tables and requests topic deletion. After successful validation, DBX immediately requests per-table topic deletion and then its run-specific Schema Registry subject, confirms absence asynchronously, and retries cleanup without changing migration success.

Tables without a usable monotonic incrementing column use a deliberately emulated one-pass bulk path: `poll.interval.ms=2147483647`, a fresh empty topic, exact equality with the frozen baseline, and immediate Source deletion after two stable polls. An offset above the baseline is duplicate-delivery failure. Bulk sources never auto-resume after interruption, and boxes have a 24-hour run limit, well below the connector's next bulk poll. Connector upgrades must regression-test this compatibility assumption.
